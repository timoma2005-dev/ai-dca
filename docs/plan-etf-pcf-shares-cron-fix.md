# ETF PCF Events deadline 与快照修复计划

> 范围：仅提供计划，不修改代码、不写 KV、不部署。以下结论来自当前工作区源码；线上版本、KV 内容和边缘耗时尚未验证。

## 1. 问题确认与方案推荐

### 当前执行链的实际问题

`runStage` 的 20 秒预算覆盖整个流程：

历史 limits/shares 读取 → 单条 PCF fallback → 当日数据整理 → shares 下载与解析 → 快照和日志预检 → 持久化 → shares projection。

历史扫描、fallback 均串行执行。快照全缺时，前置读取就可能耗尽预算，导致后面的快照和 projection 无法写入；下一次运行继续全量 fallback，形成循环。

**数量需要纠正：当前 `TARGET_CODES` 共 13 只，但 `EVENT_CODES` 仅包含 8 只深市 ETF。** 因此当前历史 fallback 上限为 **10 天 × 8 只 = 80 次**单条 KV 读，加上每天 limits/shares 快照共 20 次读取，历史阶段合计最多约 **100 次**，还未计入后续读取。130 次适用于 fallback 扩展到全部 13 只后的情形，并非当前实现。

### 方案对比

| 方案 | 改动 | 收益 | 局限与风险 |
|---|---|---|---|
| A：仅放宽 deadline | 将 20 秒提高到经实测确定的预算，例如暂定 60 秒 | 改动小，缓解冷缓存超时 | 不减少串行读取，也不消除快照写入依赖后续流程的问题；仍可能拖累 projection |
| B：修复快照生产，缩小 fallback，适度调整预算 | 将 limits 快照保存从 shares 下载链中解耦；历史快照保留 10 天查询窗口，单条 fallback 仅查必要日期、必要代码并限并发 | 消除循环依赖，降低读取量，保留现有 cron 和事件模型 | 需要明确缺失、损坏、读取失败的区别，以及历史基准选择规则 |
| C：shares 独立运行 | 为 shares 采集、projection 设置独立预算或独立调度；事件计算通过缓存衔接 | limits 和 shares 的慢源相互隔离 | 调度、数据就绪和重试更复杂；拆分后的事件日志可能出现跨 isolate 并发写 |

**推荐 B，分两步落地；C 作为后续独立优化。** A 可作为过渡措施，但不能单独作为根因修复。

实施顺序：

1. 增加分阶段耗时、读取次数、快照命中和失败原因日志，取得冷、热路径基线。
2. 当日 PCF 校验完成后，在独立、有界的保存步骤中写入 limits 快照，不再等待 shares 下载成功或整个事件阶段完成。
3. 保留 10 天历史快照窗口；fallback 优先查有交易日证据的最近必要日期，并复用已读数据。
4. 单条 fallback 使用 `mapLimit`，初始并发建议 3；显式设置总读取上限和时间预算。
5. 预留持久化预算，避免所有时间都被历史恢复和下载占用。20 秒是否保留，由边缘实测决定。
6. 若 shares 仍持续挤占预算，再实施 C。独立运行不应演变成两个任务无协调地合并写同一事件日志。

缩小 fallback 时，不能跳过最近交易日的缺失或未知值，转而使用更旧但“恰好有值”的日期制造信号。无法确认基准时应输出 `unknown` 及具体原因。

## 2. `etf-pcf-events-limits:*` 为什么写不进去，要不要修

**要修。源码能够确认执行顺序存在问题，但不能仅凭源码断言所有线上缺失都由 timeout 引起。**

当前 limits 快照不是在 PCF 抓取成功时立即写入，而是在以下步骤全部完成后才开始保存：

- 10 天历史快照及单条 fallback；
- 当日 SZSE/SSE 数据整理；
- shares 当前、历史报表下载；
- 事件日志预检；
- 所有待写快照预检。

因此，前面任何 timeout、读取异常、损坏日志或损坏快照，都可能让当日 limits 快照没有机会写入。`current` 为空时也不会创建 limits 快照；这应与写入失败分开统计。

需要逐项核查：

| 现象 | 核查方法 | 处理 |
|---|---|---|
| 保存前预算耗尽 | 记录阶段耗时、剩余预算和 `timeout` 所在阶段 | 提前独立保存 limits，收敛 fallback |
| 当日输入为空或未通过校验 | 统计输入数、通过校验数、上海业务日期 | 修复数据传递或日期问题，不写伪快照 |
| 远端快照或事件日志损坏 | 记录 key 和校验失败原因 | 导出原值，走显式修复流程，禁止静默覆盖 |
| KV 读写失败 | 区分 get、put、解析、校验错误 | 保留可重试失败，不当作缓存缺失 |

另一个需要修正的点：fallback 当前用宽泛 `catch` 忽略单条读取异常，可能把 KV 故障混同为没有历史记录。重构时应保留解析失败可跳过的策略，但对超时、基础设施读取失败明确退出或降级报告。

历史补快照应作为一次性恢复步骤：

- 仅使用通过历史校验的原始 PCF 缓存；
- 保留真实来源及可追溯时间，不伪造抓取时间；
- 不凭空补齐缺失代码，不用当前值回填历史；
- 不覆盖损坏记录；先导出、诊断；
- 不依赖补快照动作自动重发历史通知。

## 3. `etf-pcf-shares:latest` 指针格式修复确认

当前工作区的 `persistSharesProjection` 已构造以下字段：

| 字段 | 要求 |
|---|---|
| `schemaVersion` | `1` |
| `source` | 与 schema 中的 `SOURCE` 一致 |
| `date` | `YYYY-MM-DD` |
| `key` | `etf-pcf-shares:YYYYMMDD` |
| `fetchedAt` | 日期对象对应的抓取时间 |
| `expiresAt` | 与日期对象一致，并满足 schema 的 TTL 规则 |

**源码层面已具备完整指针格式；线上修复是否生效仍需确认。**

验收分三层：

1. **写入端**：日期对象先保存成功，再更新 latest；指针不能回退到更旧日期或更旧批次。
2. **读取端**：`validSharesPointer` 通过，目标对象通过校验，且两者 `fetchedAt`、`expiresAt` 一致。
3. **线上数据**：读取生产 latest 及其目标 key，确认实际部署和数据均符合约定。

需特别处理旧坏指针：当前写入器遇到不合法的已有指针会返回 `projection_pointer_failed`，不会自动纠正。应准备一次性、可审查的数据迁移，仅指向真实、有效且未过期的日期对象；不能只改 `key`，也不能延长旧数据寿命掩盖过期。

## 4. Worker 重新部署与边缘实测

### 部署步骤

1. 使用独立 `git worktree` 实施修复，避免其他任务提交混入。
2. 保存变更前基线：当前 Worker 版本、cron 配置、相关 KV 对象及阶段日志。
3. 完成下节回归检查，确认部署内容只包含本次修复。
4. 在仓库根目录执行构建预检和部署：

```bash
npx wrangler deploy --config workers/ocr-proxy/wrangler.toml --dry-run
npm run worker:deploy
```

5. 记录新版本 ID，确认目标为 `ai-dca-ocr-proxy`，KV 绑定和路由保持正确。
6. 根据核查结果执行必要的快照补齐、指针迁移；保留迁移输入和结果记录。
7. 观察下一次真实 cron，异常时回滚到已记录版本。回滚代码不会自动撤销 KV 数据迁移。

### 边缘实测方法

启动日志观察：

```bash
npx wrangler tail --config workers/ocr-proxy/wrangler.toml --format json
```

在独立测试 Worker、独立 KV namespace 中验证三种路径，关闭真实通知：

- **热路径**：历史快照齐全。
- **冷路径**：历史快照缺失，但必要的单条 PCF 存在。
- **故障路径**：shares 慢响应、KV 失败、损坏快照和坏指针。

手动触发应复用同一编排函数，并传入明确的 `scheduledTime`；如需增加诊断入口，应鉴权且限定测试环境。普通 shares API 请求不能证明 cron 已执行，也不能替代事件阶段实测。

生产读取验证：

```bash
npx wrangler kv key get 'etf-pcf-shares:latest' \
  --binding FUND_LIMIT_KV --remote \
  --config workers/ocr-proxy/wrangler.toml

curl -fsS 'https://api.freebacktrack.tech/api/etf-pcf-shares?date=latest'
```

再读取指针实际指向的日期对象，以及运行业务日对应的 `etf-pcf-events-limits:YYYYMMDD` 和事件日志。考虑 KV 可见性延迟进行有界重试，分别记录“put 已确认”和“边缘读已可见”，不要因一次读不到就重复覆盖。

## 5. 回归命令与验收标准

### 回归命令

在仓库根目录执行：

```bash
node --test test/*Pcf*.test.mjs
npm run check:refactor
npm run lint -- --quiet
git diff --check
npx wrangler deploy --config workers/ocr-proxy/wrangler.toml --dry-run
```

全量 lint 若存在既有失败，应记录基线并确认无新增；不能直接宣称检查全部通过。

### 必补测试

- 快照齐全时不触发单条 fallback。
- 全缺快照时读取次数受明确上限控制，不再默认遍历全部日期的所有代码。
- shares 超时或失败时，当日合法 limits 快照仍可独立保存。
- fallback 的 timeout、KV 读取失败不会被当作“空基准”。
- 最近交易日缺失或未知时，不误用更旧日期生成事件。
- 损坏数据不被静默覆盖；持久化失败不会报告整个阶段成功。
- latest 格式、目标对象一致性、坏指针迁移、日期写失败、指针写失败和不回退。
- 重跑保持事件唯一及最早 `when_detected`；T-1 shares 信号仍归属正确日期。

### 验收标准

- 冷、热路径均在配置预算内完成，并留有明确写入余量；建议目标至少保留总预算的 20%。
- 冷路径连续至少 3 次运行无超时，记录真实 KV 读取次数及总耗时。
- limits 快照成功保存后，后续运行能命中快照，读取量明显下降。
- shares 源故障不阻断 limits 保存和可计算的限额事件；projection 失败单独报告。
- latest 与显式日期接口返回一致有效的数据；旧数据过期仍正确返回缺失状态。
- 同一业务日重跑不重复累计事件、不回退指针、不新增重复通知。
- 原有两个 cron 的职责和失败隔离保持通过。

## 6. 风险分析

| 风险 | 当前依据与应对 |
|---|---|
| 事件推送重复 | `runEtfPcfDailyRefresh` 在 `events.ok` 后发送 `detectedEvents`。重跑仍可能再次返回同一事件，因此日志去重不能替代通知去重。核查现有发送器的持久化幂等机制，并覆盖重复运行测试 |
| 推送幂等键口径不同 | 事件身份使用日期、代码、信号类型、basis；notify handler 的 `eventId` 使用代码、日期、tier。需明确 net/total 合并以及 tier 升级策略，避免误去重或重复推送 |
| 快照恢复触发历史通知 | 补快照与事件重算分开执行；恢复演练关闭投递，生产重算只发送符合既定时间窗口的事件 |
| KV 跨 isolate 丢失更新 | 当前队列、去重和一秒写间隔保存在 `WeakMap`，仅保护本 isolate。优先保留事件日志单一写入者；如实施独立任务共同写日志，需另行引入跨实例串行协调 |
| 超时后仍有在途写入 | `abortable` 停止等待不代表底层 KV put 被撤销。超时后应按“结果未知”处理，并通过幂等重试及读回核验恢复 |
| 提前保存后部分成功 | 明确区分快照已保存、事件未完成、projection 未完成。不能因快照成功就令 `events.ok=true` 或启动通知 |
| cron 相互影响 | 保持 UTC `0 1 * * *` 执行 ETF 链，`0 12 * * *` 执行原场外刷新；分别验证异常隔离、上海日期及跨日延迟 |
| 独立 shares cron 读到未就绪数据 | 若后续采用方案 C，以业务日期、来源校验及实际数据就绪状态衔接，设置有界重试，不能仅靠固定错开几分钟 |
| 单纯扩大 deadline 挤占总预算 | 先测完整 SSE → SZSE → events 链剩余时间，再确定阶段预算；不能只证明 events 单独运行成功 |
