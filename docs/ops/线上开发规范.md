# ai-dca 线上开发与发布规范（CN 机 / Cloudflare）

目的：任何改动都只有一个来源（Git 仓库），线上热修不会被下一次发布悄悄覆盖。

## 1. 唯一事实来源
- 前端、Worker、CN 机服务的代码**以 GitHub `lovexlc/ai-dca` 为准**。线上环境只放构建产物，不作为源码。
- 禁止直接修改线上构建产物（`/var/www/ai-dca-cn-releases/*` 里的 js/css）或 Cloudflare 线上 bundle，除非按第 4 节走热修流程。
- CN 机上的 `/root/ai-dca` 不是最新代码（停在 2026-09），不能用它构建或部署，用之前先 `git fetch` 并确认分支和提交号。

## 2. 发布前必须做
1. 先同步再构建：`git pull --rebase`（或基于最新的 `origin/<发布分支>`），确认本地包含线上当前版本的提交。
2. **查热修标记**：发布前读取线上当前版本：
   - 前端：`cat /var/www/ai-dca-cn/HOTFIX.json`。存在且 `source_synced` 为 `false`，说明线上有未进仓库的热修，**停止发布**，先把热修合进源码。
   - Worker：查看 Cloudflare 脚本的部署说明/版本信息，或 `docs/ops/HOTFIX_LOG.md` 里未关闭的条目。
3. 本地跑完：相关 `node --test`、`npm run check:refactor`、`npm run lint -- --quiet`、`git diff --check`。
4. 构建产物带上提交号：发布目录里写 `RELEASE.json`：`{commit, branch, builtAt, builtBy}`。

## 3. 发布方式（CN 机前端）
- 新版本放进新目录 `/var/www/ai-dca-cn-releases/<YYYYMMDDHHMMSS>/`，**不要原地覆盖已有目录或已有文件名**（`/react-assets/` 是一年 immutable 缓存，同名改内容，用户拿不到新版本）。
- 用原子切换：`ln -sfn <新目录> /var/www/ai-dca-cn.tmp && mv -T /var/www/ai-dca-cn.tmp /var/www/ai-dca-cn`。
- 保留最近 5 个版本，回滚 = 把软链指回上一个目录。
- 切换后立刻验收：打开 `https://fast.freebacktrack.tech/home.html?tab=<改动页>`，确认页面正常、接口 200、无控制台报错，手机宽度（390px）也看一遍。
- Worker 发布：`wrangler deploy` 必须从仓库执行；**不要**用 Cloudflare API 直接 PUT 脚本内容，除非是热修。

## 4. 热修流程（线上紧急改动）
只在线上故障、等不及走仓库时使用。
1. 改之前先备份线上版本（前端：保留原发布目录；Worker：下载当前 bundle 存档）。
2. 前端热修也要发成**新目录**，并在目录根写 `HOTFIX.json`：
   `{ "hotfix": "说明", "base_release": "基于哪个目录", "by": "谁", "at": "时间", "source_synced": false }`
3. 在仓库 `docs/ops/HOTFIX_LOG.md` 追加一条（日期、改了什么、改了哪些文件、线上位置、回滚方式）。
4. **24 小时内把改动合进源码**并走正常发布。新发布的 `RELEASE.json` 写上关闭的热修条目，然后把 HOTFIX_LOG 那条标为已关闭。
5. 热修没合进源码之前，任何人（包括 AI agent）都不能从仓库发布覆盖它。

## 5. 接口和前端契约
- Worker 返回结构变了（加字段、放开校验条件），前端的严格校验（如 `validateSharesProjection`）必须同一个 PR 一起改，并且**先发前端、再发 Worker**，避免前端把新数据判为无效。
- CN 机的 `etf-mirror` 只透传，不改结构；Worker 结构变化后不用改它，但要等它刷新（默认 5 分钟）。

## 6. 多人 / 多 agent 协作
- 同一时间只允许一个人/agent 发布。发布前在 `docs/ops/DEPLOY_LOCK`（或群里）占锁，发布完释放。
- AI agent 必须先读本文件和 `AGENTS.md`，发布前执行第 2 节检查，发布后在 HOTFIX_LOG / 发布记录里留痕。

## 前端启动：Vite preview + Nginx（2026-10-20 起）

- 进程：supervisor 程序 `ai-dca-frontend`（配置追加在 /etc/market-collector-supervisord.conf，副本 deploy/cn/ai-dca-frontend.supervisor.conf），命令 `vite preview --outDir /var/www/ai-dca-cn --host 127.0.0.1 --port 4173 --strictPort`。
- 管理：`supervisorctl -c /etc/market-collector-supervisord.conf status|restart ai-dca-frontend`
- Nginx：站点 ai-dca-cn-5000 的 `/` 和 `/react-assets/` 转发到 127.0.0.1:4173（资产加 immutable 头），vite 不可用时 502/503/504 回落到同一发布目录的静态文件；`/api/*` 路由不变。配置副本 deploy/cn/nginx-ai-dca-cn-5000.conf。
- 发布：`bash scripts/cn-frontend/release.sh`（构建到 /var/www/ai-dca-cn-releases/<时间戳>，写 RELEASE.json，切软链，重启 vite，健康检查失败自动回滚）。
- 回滚：`bash scripts/cn-frontend/rollback.sh <时间戳>`。
- 机器上有 http(s)_proxy 环境变量，本机 curl 需加 `--noproxy '*'`。

## 强制栅栏：只改源码，不改产出物（2026-10-20 起）

1. **发布入口唯一**：`scripts/cn-frontend/release.sh`。工作区（src/shared/public/入口 html/vite.config.js/package.json）有未提交改动，或 HEAD 未 push 到 origin，直接拒绝发布。
2. **产出物指纹**：每个发布目录写入 RELEASE.json（commit）和 MANIFEST.sha256，并设为只读。`scripts/cn-frontend/verify.sh [目录]` 校验：commit 在仓库里、文件与 MANIFEST 一致、无多余文件。
3. **守护回滚**：supervisor 程序 `ai-dca-frontend-guard`（scripts/cn-frontend/guard.sh）每 60 秒校验线上目录，不通过即回滚到最新一个校验通过的发布并重启 vite，日志 /var/log/supervisor/ai-dca-frontend-guard.log。
4. **回滚也受限**：rollback.sh 只接受通过 verify.sh 的目录；旧的热修目录（无 MANIFEST）不能再上线。
5. **Agent 钩子**：`.claude/settings.json` 的 PreToolUse 钩子（scripts/agent-guard/pretool-guard.mjs）拦截 Edit/Write 到仓库外路径、构建产物目录，以及 Bash 中写 /var/www/ai-dca-cn*、发布目录、react-assets、直接 `vite build --outDir` 到线上的命令。Codex 等无钩子的 agent 由 AGENTS.md 约束 + 第 2、3 条兜底。
6. 以前的「直接改 bundle 热修 + HOTFIX.json」流程作废。

## 自动发布（push 即上线）

- supervisor 程序 `ai-dca-frontend-autorelease`（scripts/cn-frontend/autorelease.sh）每 60 秒 `git fetch origin`，origin/cn 有新的前端相关提交（src/shared/public/入口 html/vite.config.js/package.json）时，fast-forward 本地分支并调用 release.sh。
- 所以流程是：改源码 → commit → push origin cn → 约 1~2 分钟后自动上线。不涉及前端文件的提交不会触发构建。
- CN 工作区有未提交前端改动或本地分支分叉时跳过并记日志 /var/log/supervisor/ai-dca-frontend-autorelease.log，需人工处理。
